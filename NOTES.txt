1. Naming 
  "bulk pay" seems descriptive and obvious enough for anyone to understand (including AI)

2. Technical stack

  At 1 endpoint and 2 tables building full Rails app seems to be pure overhead. 
  In order to build small clean solution focused on performance and transactional safety I'm choosing pure Rack app with 
    minimal library surface which can be transplanted on existing Rails app easily, or used as a standalone microservice. Other alternatives might be Sinatra or Roda.
  For ORM I'm choosing ActiveRecord as most popular Ruby db library. 
  Web server choice is conservative - puma.
  Testing with Rspec.
  Processing is split into validation phase (ProcessPayments::Request) and charging phase (ProcessPayments::Charge).

3. Transactional safety
  I decided to build atomic API - response 201 means all data was succesfully updated. Each request is one short transaction: lock all firms of the request in id order, check payer balance, update balances, insert payments. Same lock order means that even if firms A and B charge each other at the same time they just wait for each other instead of deadlocking. Lock timeout or deadlock with some other writer means HTTP 503 as a signal to try again - nothing is written in that case.
  First version used NOWAIT locks with randomized retries, but it turned every overlap on a busy firm into 503. If a single busy firm ever becomes a bottleneck, next step would be append-only ledger with credits applied asynchronously.
  I decided not to use any kind of async, as Option A - returning HTTP 201 after checking funds and delaying actual processing to background worker would create nasty race conditions, and Option B - implementing fully async API (upload - poll for results) will impose larger load on API consumer. Also that would be against task requirements.

4. Idempotency
  Same batch can be legitimately sent twice (e.g. monthly fees), so only the client knows if a request is a retry. I decided to require Idempotency-Key header, unique per payer firm. Successful requests are stored as payment batches - repeated key gets 201 without charging again, same key with a different request gets 422. Failed requests are not stored, so they can be retried with the same key.
  Key is checked after the payer is locked, so a duplicate sent while the original is still running just waits for it.

5. Connections and deployment
  Plain Rack has no Rails executor, so App returns db connections to the pool after each request itself.
  Puma threads and db pool size come from the same MAX_THREADS. instances * WEB_CONCURRENCY * MAX_THREADS must stay below postgres max_connections, otherwise PgBouncer is needed.
  Request body size limit is supposed to be handled by outer layer like nginx or auth proxy - largest valid request is about 600KB.

6. Intentionally not implemented: authorization, monitoring

7. Starting app
  docker compose up --build - app is on port 9292 (APP_PORT to change), migrations run on start.
  Seed: docker compose exec app bundle exec rake db:seed
  Tests: bundle exec rspec (needs local postgres)
