## 1. Assumptions
  I assumed that best way ot go is to build versatile minimalistic service suitable both for standalone or integrated working. Because of that I skipped heavy frameworks and concetrated on business-critical values of robustness and data integrity. 

  I managed to keep whole business logic in `app/` below 300 LOC, so it's observable and easy to modify. I prefer not to have overly complex architecture unless absolutely necessary, because every line of code has maintenance cost which multiplies with using AI.

  As for DB schema and API request format I tried to be exact, so examples of firm-inserting SQL and JSON from the spec can be used without any modification. Nevertheless I added another table and timestamps to `payments` table - because it seems to be really important to me.

  One thing which worried me in requirements was a lack of any mentions of protection of request duplications, so I added mandatory idempotency key and replay mechanism.

  Another spec extension was adding a lot more of HTTP codes to initial HTTP 201/422. This solution returns a range from HTTP 400 when incoming JSON is malformed up to HTTP 503 when concurrent requests cannot be fulfilled.

  Also I assumed that we can add layers like auth and monitoring afterwards and put them in "Further work" section in README.

## 3. Technical choises
  
### 3.1 Naming 

  "bulk pay" seems descriptive and obvious enough for anyone to understand (including AI)

### 3.2 Technical stack

  At 1 endpoint and 2 tables building full Rails app seems to be pure overhead. 

  In order to build small clean solution focused on performance and transactional safety I'm choosing pure Rack app with minimal library surface which can be transplanted on existing Rails app easily, or used as a standalone microservice. Other alternatives might be Sinatra or Roda.

  For database work I'm choosing ActiveRecord as most popular Ruby DB ORM. Web server choice is conservative - puma (maybe it worth to try falcon as potentialy more capable, but that requires more testing). Testing with Rspec.

  Latest version of Ruby (4.0.7), though fully 3.4 compatible.

### 3.3 Transactional safety

  API endpoint is atomic - response 201 means all data was succesfully updated. Each request is one short transaction: lock all firms of the request in id order, check payer balance, update balances, insert payments.

  Same lock order means that even if firms A and B charge each other at the same time they just wait for each other instead of deadlocking.

  Lock timeout or deadlock with some other writer means HTTP 503 as a signal to try again - nothing is written in that case.

  I decided not to use any kind of async, as Option A - returning HTTP 201 after checking funds and delaying actual processing to background worker would create nasty race conditions, and Option B - implementing fully async API (upload - poll for results) will impose larger load on API consumer. Also that would be against task requirements.

### 3.4 Idempotency

  Same batch can be sent twice (e.g. monthly fees), so only the client knows if a request is a retry. We require Idempotency-Key header, unique per payer firm. Successful requests are stored as payment batches - repeated key gets 201 immediately, same key with a different request gets 422. Failed requests are not stored, so they can be retried with the same key.
  Key is checked after the payer is locked, so a duplicate sent while the original is still running just waits for it.

### 3.5. What was not implemented
  
  Intentionally not implemented: authorization, monitoring, request size capping
